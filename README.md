# qyn-dsh-plugin —— 把内核封成 DSH 工具

> 把 Python 确定性内核（[`AGENT/qyn.py`](qyn.py（独立仓库根）)）封装成 DSH 工具，
> 让**自然语言对话可以安全地更改** `rules.json` / `data.json`。

---

## 1. 设计：薄适配层

```
模型（DSH）        理解自然语言：用户说"结课论文改到15号"
     │             决定要不要调工具、调哪个、传什么参数
     ▼
本插件（TS，薄）   注册工具 + 参数 schema + 调内核 + 回传 JSON
     │             ★ 不含任何业务逻辑
     ▼
内核（Python，厚） 日期计算、ISO 周、schema 校验、保守匹配
     │
     ▼
JSON 数据          唯一真源
```

**为什么插件是薄的**：内核已被整套端到端测试钉住（ISO 周跨年、schema 严格校验、
保守匹配拒绝……；条数与实测命令见
[`docs/ARCHITECTURE.md`](（架构文档见项目主页）) 的「验证口径」一节 —— **别在别处抄这些数字**）。
把这些逻辑重写进 TypeScript，等于把踩过的坑再踩一遍。
**零 npm 依赖**（只用 node 内置模块）—— 因为插件要装到没有外网的中控机上。

**为什么这样就能"自然语言改 JSON"**：模型负责听懂，内核负责保证结构合法。
于是模型可以随便用自然语言表达，但**永远写不出坏 JSON** —— 这正是
[DEV_STYLE.md](（开发风格见项目主页）) 那条"确定性→代码、语义→模型"。

## 2. 工具清单（12 个）

| 工具 | 作用 |
|---|---|
| `qyn_state` | 读全量现状（规则 / 作息 / **带日期的**课表 / 周期任务 / 待办清单 / **上次规划 `last_plan`**） |
| `qyn_week` | 某一周课表的完整回读（含教室、停课依据）——录完课表必须念 |
| `qyn_sessions` | 未来 N 天的课次与待办（按**实际日期**，与周次无关） |
| `qyn_show` | 取某一条的 `detail`（列表里只有 `gist`；归档条目默认只回列表字段） |
| `qyn_anomalies` | 读**确定性**异常清单（锚不到日期、课表为空、规则 scope 失效、数据久未维护） |
| `qyn_sync` | **物化**：课表 + 周期任务 → 待办清单（幂等，**不做周推算**） |
| `qyn_history` | 已滚出热文件的条目（单次最多 50 条；只用于用户明确回溯，**不主动翻**） |
| `qyn_apply` | ★ **唯一写入口**：`schedule`（课表 / 周期任务）、`rules`（规划规则）、`list`（作业 / 提醒 / 一次性任务）；`{upsert, remove}` 增量或整段替换 |
| `qyn_mark` | 标记状态（**名称需完全一致**，否则拒绝并返回 `known_tasks`） |
| `qyn_brief` | 生成**现成排版的正文**：`plan` 规划（不含课）/ `schedule` 日程（含课）/ `todo` 待办两张表 —— **原样发出**，不要自己拼版 |
| `qyn_review_plan` | 规划自检：撞课 / 时段重叠 / 漏排（交出去之前自己先审一遍） |
| `qyn_plan_snapshot` | 存规划快照（下次 `qyn_state` 会带回来） |

> 保守原则在工具层就生效：`qyn_mark` 只接受**名称完全一致**的任务，不一致会把已知任务列表
> 交回模型去回询用户 —— 不猜。`qyn_apply` 的删除是**不拦但如实报**：
> 返回里的 `check_this.missing` 就是"你要删的没匹配上"（名字写错了），`replaced` 是
> "同身份被覆盖且名字变了"（可能误伤了别的东西）—— 写入照样完成，但模型必须当场纠正。
>
> ★ **没有周概念**：课表只认具体日期（`第6周` 这类值会被内核拒绝）；
> 作业日期靠锚到课次，不靠"第几周"推算。
>
> ★ **唯一写入口**：`qyn_apply`（课表 → `schedule`，规则 → `rules`，作业/提醒 → `list`）。
> 内核侧同样只有 `apply` 一个写子命令 —— 没有第二套 `set-*`（已合并删除）。

## 3. 怎么装

插件按常规 node 解析路径放：**`<DSH_HOME>/profiles/<profile>/node_modules/qyn-time`**。

```bash
# 本机彩排（会自动完成上面的拷贝）
python （演练脚本在项目主页）

# 手动部署时就是这么一步
cp -r （插件目录） <DSH_HOME>/profiles/<profile>/node_modules/qyn-time
```

profile 的 `cordis.patch.yml` 里已有一条挂载行：

```yaml
- insert:
    - id: qyn-time
      name: qyn-time
```

`repoRoot`（内核所在目录）**刻意不写死在 patch 里** —— 开发机与中控机路径不同。
插件按环境变量取，缺省用进程 cwd：

| 环境 | `QYN_REPO_ROOT` |
|---|---|
| Windows 开发机 | `<repo-root>` |
| Linux 中控机 | `<deploy-dir>`（Agent 那套 release 软链；单元里就是这个值） |

> ⚠️ **别写成 `<部署目录>`** —— 那是**状态墙**那套（→ `<部署目录>`）。
> 写错了插件就找不到内核。两套部署的分工见

## 4. 自测

```bash
node test/plugin.test.mjs
```

这套断言**不需要模型、不需要凭据**：用假 `ctx` 装载插件，验证工具契约与参数 schema 形状，
并**真的去调内核** —— 读工具打真实仓库（只读），写工具打临时副本（不碰真实数据）。
条数以该脚本自己的输出为准（实测命令上面这条）。

`python （演练脚本在项目主页）` 另外会启动一次真实 profile，断言启动输出里出现
`[qyn-time] 已注册 12 个工具` —— 这是"插件被真正加载"的唯一可靠信号
（插件日志只走 `ctx.logger` 时，界面上一片安静，很容易误判成没加载）。
